# V0.3 Private Release Candidate Spec

Status: Implemented; local/private RC readiness pass; hosted gate infrastructure-blocked
Date: 2026-07-14

This spec describes the target contract for the current private branch. The
pinned subject commit has completed local and isolated-Linux acceptance, but
this is not a release or merge approval: the current official version is
still v0.2.0, there is no v0.3 tag/Release, and repository visibility has not
changed.

## 1. Goals

V0.3's theme is **trust first: explain first, preview first, modify last**.
This phase completes public-readiness work inside the private repository,
but does not execute the public release, a formal tag, or a Public Beta
release.

V0.3 must answer four questions at once:

1. Who installed and manages this binary?
2. What is hukou about to do, and can it be inspected with zero writes first?
3. After an upgrade or repair failure, can the current state and true
   history be deterministically recovered?
4. Can an unfamiliar user understand, install, verify, and safely report
   issues?

## 2. Product boundary

- hukou manages single-file CLIs on the real PATH that no one else owns and
  that the user has explicitly adopted.
- `upgrade --all` refers only to all hukou-adopted entries.
- Homebrew, mise, aqua, npm, Cargo, and similar tools continue to own their
  own entries.
- Whole-machine upgrades integrate through a Topgrade custom command; V0.3
  does not implement a cross-manager executor.
- GUI apps, the OS, kernel, firmware, drivers, VPNs, and security software
  are out of the default plan.

## 3. CLI contract

### 3.1 `explain`

```text
hukou explain <name|path> [--json]
```

- A bare name explains every same-named candidate on PATH; the first entry
  is the actual resolved result, and the rest are marked shadowed.
- An explicit path explains only that file.
- Output includes path, real path, kind, source, package, version,
  confidence, evidence, and shadowed.
- Detector load issues surface as warnings; they are never fabricated into
  exact attribution.
- Zero network, zero writes; a nonexistent target returns nonzero.

### 3.2 `adopt --dry-run`

```text
hukou adopt <name|path> [owner/repo] [--tag TAG] [--local] [--force] --dry-run [--json]
```

- dry-run checks file type, permissions, SHA, provenance, repo/tag,
  conflicts, and the planned write.
- dry-run creates no data root, lock, store, manifest, backup, or
  transaction, and does not GC.
- A pending transaction only fails read-only with a hint; it is not
  recovered.
- The real adopt re-checks every mutable precondition after acquiring the
  lock; it must not reuse a stale dry-run result.
- In V0.3, `--json` is only used together with `--dry-run`.

### 3.3 `outdated`

```text
hukou outdated [name ...] [--json] [--asset FILTER]
```

- With no name given, it checks all hukou entries.
- local entries are marked local and never go over the network.
- Drifted entries fail closed before any GitHub request.
- It only queries release metadata and selects an asset; it never
  downloads or writes state.
- current/outdated/local are normal results; network, state, or selection
  errors cause a nonzero exit.
- It reuses the same update checker as `upgrade --dry-run`.

### 3.4 `policy`

```text
hukou policy show [name] [--json]
hukou policy set <name> [--mode semver|github-latest] [--channel stable|prerelease]
                 [--pin TAG|--unpin] [--rollback-depth N]
```

- `pinned_tag` takes priority over channel; an exact tag uses a
  release-by-tag query.
- stable never selects a draft/prerelease.
- semver mode only accepts strictly sortable versions; a normalized-equal
  result is a no-op, and downgrades are rejected by default.
- When explicitly switching an existing entry to semver, if it is local or
  the current tag is not a strict `X.Y.Z` (a lowercase `v` prefix and a
  valid suffix are allowed), the switch must be rejected with zero state
  change.
- The legacy `github-latest` mode is only for explicitly selected
  non-SemVer upstreams.
- Policy changes are saved atomically inside the state lock; they never
  touch the live binary.

### 3.5 `repair`

```text
hukou repair plan --action recover-transaction --output PLAN
hukou repair plan --action restore-manifest-backup --output PLAN
hukou repair apply --plan PLAN
```

- doctor remains strictly read-only; no `--fix` flag is added.
- A plan includes schema, action, data-root identity, preconditions, a
  state fingerprint, and the generation time.
- apply creates/uses `state.lock` and recomputes the fingerprint inside the
  lock; on a mismatch it must not modify business state such as live,
  store, manifest, backup, or journal. This contract is "zero
  business-state writes," not "absolute zero file writes" — the plan file
  and lock traces must each be documented separately.
- `recover-transaction` reuses the existing WAL recovery.
- `restore-manifest-backup` is only available when the primary manifest is
  missing/invalid, the backup is semantically valid, and its entries match
  the live SHA.
- repair-all, orphan deletion, directory quarantine, and manifest merging
  are not supported.

### 3.6 `support bundle`

```text
hukou support bundle --output FILE
hukou support bundle --format json
```

- No network by default; zero writes other than the explicit output.
- File output permissions are `0600`.
- It includes version, OS/arch, redacted doctor output, manifest/policy/
  history summaries, and transaction/store topology.
- It excludes binaries, WAL payloads, tokens, environment variables,
  usernames, HOME, private repos, and raw absolute paths.
- It never auto-uploads; if `--include-paths` is implemented, it must be
  explicit and warn before output.

## 4. Manifest schema v2

### 4.1 Migration

- schema 0/1 can be deterministically migrated to 2.
- The decoder must select its field set based on the declared schema:
  schema 2 is rejected when required state such as policy/retention/
  history is missing; schema 0/1 is rejected when it carries v2-only
  top-level or entry fields — new semantics must never sneak in through
  legacy migration.
- Migration never guesses history from store mtime.
- Each old entry creates a synthetic root activation using its current
  tag/SHA.
- Future schemas must be rejected on read.
- V0.2 reading schema v2 must fail, to avoid losing new fields on save.

### 4.2 Activation lineage

Every event includes at least ID, parent, operation, tag, SHA,
activated_at, and an optional reverts ID.

- adopt creates the root event.
- upgrade creates a child of the current event.
- A default rollback restores the current event's parent and generates a
  new activation record for the operation.
- `A→B→C→B→A` is the deterministic target; it must never fall back to C
  based on directory timestamps.
- history and active state must land in the same after-manifest and be
  committed together through the existing WAL.
- An event tag must be a safe single path component; within the same
  lineage, the same tag may only ever bind to the same SHA-256, so the
  logical history never interprets the same version name as different
  bytes.

### 4.3 Retention

- The default rollback depth is 2.
- current, original, installed pinned artifacts, and the most recent N
  lineage targets are protected; when an unfinished transaction exists, the
  entire prune is skipped with zero deletions, so its references are never
  removed.
- prune generates and fully validates the deletion plan before any
  deletion begins.
- mtime plays no part in protection decisions.
- Any anomaly in a protected ref's type/SHA/path results in zero
  deletions.

## 5. JSON stability

- explain, adopt plan, outdated, policy, repair plan, and support report
  each carry their own `schema_version`.
- Arrays and text output use deterministic ordering.
- JSON fields use English only and never change with locale.
- Adding fields is allowed for backward compatibility; removing or
  redefining a field must bump the corresponding report schema.

## 6. Language and documentation

- The public README, CLI help, errors, warnings, and normal output default
  to English.
- `README.zh-CN.md` retains the full Chinese text.
- Script output never changes automatically based on `LANG`; any future
  localization must be explicit opt-in.
- Documentation must distinguish "implemented," "RC verified," and
  "publicly released."

## 7. Distribution readiness

- The recommended root license for original code is Apache-2.0;
  third-party files keep their own licenses and provenance headers.
- The release snapshot includes LICENSE, THIRD_PARTY_NOTICES, LICENSES,
  README, four-platform archives, checksums, and an SBOM.
- CI/release actions pin full commit SHAs, and tokens are read-only by
  default.
- The installer does not use sudo and does not modify shell rc files by
  default; it must verify the checksum.
- The installer only accepts HTTPS for production URLs; in non-force mode
  a dangling symlink is treated as existing. The final directory-entry
  commit uses `link(2)` atomic no-replace when Perl is available, and
  `rename(2)` under force; on Linux without Perl it falls back to
  `ln -T`/`mv -T` no-target-directory, and fails closed when the safety
  primitive is unavailable. A directory, a symlink-to-directory, and a
  post-precheck race must all be rejected; an archive must contain exactly
  one target executable member, and a duplicate member must be rejected.
- The Homebrew formula and public fixture repo contents create remote
  objects only after a later public Go/No-Go decision; this round can be
  verified in a local staging directory.

## 8. Acceptance gates

1. All newly added read-only commands prove zero writes; commands that
   need the network prove their request scope and zero downloads.
2. v1→v2, activation, policy, retention, repair, and support-privacy unit
   tests pass.
3. Existing WAL/doctor/store safety tests show no regression.
4. macOS and Linux ordinary/race tests pass; the four build targets and
   double builds are consistent.
5. Installer, release snapshot, and LICENSE/notices/SBOM checks pass.
6. Documentation, code, the change record, and the verification report are
   consistent.
7. The internal claims-vs-evidence review verdict is pass, or every
   partial/fail is closed before the RC.
8. If GitHub-hosted CI did not run due to private billing, it must be
   marked as an external gate; it must not be called a pass.

## 10. Non-goals

- Making the repository public and the formal Public Beta release.
- Cross-manager upgrade execution and unified rollback.
- Windows, GUI, self-update, and default telemetry.
- A general-purpose registry, dependency resolution, and building from
  source.
