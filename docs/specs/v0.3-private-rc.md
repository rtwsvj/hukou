# V0.3 Private Release Candidate 规格

状态：Implemented；local/private RC readiness pass；hosted gate infrastructure-blocked
日期：2026-07-14

本规格描述当前私有分支的目标契约。固定 subject commit 已完成本地与隔离 Linux
验收，但这不是发布或合并批准：当前正式版本仍是 v0.2.0，没有 v0.3 tag/Release，
repository visibility 没有改变。

## 1. 目标

V0.3 的主题是 **trust first：先解释、先预览、再修改**。本阶段在 private 仓库内完成可公开准备，但不执行公开、正式 tag 或 Public Beta 发布。

V0.3 必须同时回答四个问题：

1. 这个二进制是谁安装和管理的？
2. hukou 准备做什么，能否在零写入状态下先看清？
3. 升级或修复失败后，当前状态和真实历史是否可确定恢复？
4. 陌生用户能否理解、安装、验证并安全报告问题？

## 2. 产品边界

- hukou 管理真实 PATH 中无人负责、被用户显式收编的单文件 CLI。
- `upgrade --all` 只表示全部 hukou-adopted entries。
- Homebrew、mise、aqua、npm、Cargo 等继续拥有自己的条目。
- 全机升级通过 Topgrade custom command 集成；V0.3 不实现跨管理器执行器。
- GUI、OS、内核、固件、驱动、VPN 和安全软件不进入默认计划。

## 3. CLI 契约

### 3.1 `explain`

```text
hukou explain <name|path> [--json]
```

- 裸名称解释 PATH 中所有同名候选，第一项是实际解析结果，其余标记 shadowed。
- 显式路径只解释该文件。
- 输出 path、real path、kind、source、package、version、confidence、evidence、shadowed。
- detector 加载问题作为 warning，不伪造成 exact attribution。
- 零网络、零写入；不存在目标返回非零。

### 3.2 `adopt --dry-run`

```text
hukou adopt <name|path> [owner/repo] [--tag TAG] [--local] [--force] --dry-run [--json]
```

- dry-run 检查文件类型、权限、SHA、来源、repo/tag、冲突和计划写入。
- dry-run 不创建 data root、lock、store、manifest、backup、transaction，也不 GC。
- pending transaction 只读失败提示，不恢复。
- 真正 adopt 取得锁后重新检查全部可变前置条件；不得复用旧 dry-run 结果。
- `--json` 在 V0.3 仅与 `--dry-run` 同时使用。

### 3.3 `outdated`

```text
hukou outdated [name ...] [--json] [--asset FILTER]
```

- 无名称时检查全部 hukou entries。
- local 条目标记 local，不联网。
- drifted 条目在请求 GitHub 前失败关闭。
- 只查询 release metadata 和选择资产；不下载、不写状态。
- current/outdated/local 是正常结果；网络、状态或选择错误导致非零。
- 与 `upgrade --dry-run` 复用同一 update checker。

### 3.4 `policy`

```text
hukou policy show [name] [--json]
hukou policy set <name> [--mode semver|github-latest] [--channel stable|prerelease]
                 [--pin TAG|--unpin] [--rollback-depth N]
```

- `pinned_tag` 优先于 channel；精确 tag 用 release-by-tag 查询。
- stable 不选择 draft/prerelease。
- semver 模式只接受严格可排序版本，normalized equal 是 no-op，默认拒绝降级。
- 显式把已有 entry 切换为 semver 时，local 或当前 tag 非严格 `X.Y.Z`（允许小写 `v` 与合法 suffix）必须拒绝且零状态变化。
- legacy `github-latest` 仅用于明确选择的非 SemVer 上游。
- policy 修改在 state lock 内原子保存；不触碰 live binary。

### 3.5 `repair`

```text
hukou repair plan --action recover-transaction --output PLAN
hukou repair plan --action restore-manifest-backup --output PLAN
hukou repair apply --plan PLAN
```

- doctor 继续严格只读，不增加 `--fix`。
- plan 包含 schema、action、data-root identity、前置条件、状态 fingerprint 和生成时间。
- apply 会创建/使用 `state.lock`，并在锁内重新计算 fingerprint；不匹配时不得修改
  live、store、manifest、backup 或 journal 等业务状态。该契约是“零业务状态
  写入”，不是“绝对零文件写入”；plan 文件和 lock 痕迹都必须单独说明。
- `recover-transaction` 复用现有 WAL recovery。
- `restore-manifest-backup` 仅在主 manifest 缺失/无效、backup 语义有效且其 entries 与 live SHA 一致时可用。
- 不支持 repair-all、orphan 删除、目录 quarantine 或 manifest 合并。

### 3.6 `support bundle`

```text
hukou support bundle --output FILE
hukou support bundle --format json
```

- 默认无网络；除显式输出外零写入。
- 文件输出权限为 `0600`。
- 包含版本、OS/arch、脱敏 doctor、manifest/policy/history 摘要和 transaction/store topology。
- 不包含二进制、WAL payload、token、环境变量、用户名、HOME、私有 repo 或原始绝对路径。
- 不自动上传；`--include-paths` 如实现必须显式且在输出前警告。

## 4. Manifest schema v2

### 4.1 迁移

- schema 0/1 可确定迁移到 2。
- decoder 必须按声明 schema 选择字段集合：schema 2 缺 policy/retention/history 等
  必填状态时拒绝；schema 0/1 携带 v2-only 顶层或 entry 字段时拒绝，不能借 legacy
  migration 偷渡新语义。
- 迁移不依据 store mtime 猜测历史。
- 每个旧 entry 以当前 tag/SHA 创建 synthetic root activation。
- 未来 schema 必须拒绝读取。
- V0.2 读取 schema v2 必须失败，避免保存时丢失新字段。

### 4.2 Activation lineage

每个 event 至少包含 ID、parent、operation、tag、SHA、activated_at 和可选 reverts ID。

- adopt 创建根事件。
- upgrade 创建当前事件的 child。
- 默认 rollback 恢复当前事件 parent，并生成新 activation 记录本次操作。
- `A→B→C→B→A` 是确定性目标；不得根据目录时间回到 C。
- history 和 active state 必须进入同一 after-manifest，并由现有 WAL 一起提交。
- event tag 必须是安全单路径组件；同一 lineage 内同一个 tag 只能绑定同一 SHA-256，
  避免逻辑历史把相同版本名解释成不同字节。

### 4.3 Retention

- 默认 rollback depth 为 2。
- 保护 current、original、已安装的 pinned artifact 和最近 N 个 lineage 目标；存在 unfinished transaction 时整个 prune 跳过并零删除，因此不会删除其引用。
- prune 先生成并完整验证删除计划，再开始删除。
- mtime 不参与保护决策。
- 任一 protected ref 类型/SHA/路径异常时零删除。

## 5. JSON 稳定性

- explain、adopt plan、outdated、policy、repair plan、support report 各自带 `schema_version`。
- 数组和文本输出使用确定性排序。
- JSON 字段只使用英文，不随 locale 变化。
- 增加字段允许向后兼容；删除或改义必须提升对应 report schema。

## 6. 语言与文档

- 公共 README、CLI help、错误、警告和正常输出默认英文。
- `README.zh-CN.md` 保留完整中文。
- 不根据 `LANG` 自动改变脚本输出；未来本地化必须显式 opt-in。
- 文档必须区分“implemented”“RC verified”“publicly released”。

## 7. 分发准备

- 原创代码根许可证建议 Apache-2.0；第三方文件保留各自许可证和来源头。
- Release snapshot 包含 LICENSE、THIRD_PARTY_NOTICES、LICENSES、README、四平台 archive、checksums 和 SBOM。
- CI/release actions 固定完整 commit SHA，默认 token read-only。
- 安装器默认不 sudo、不改 shell rc，必须验证 checksum。
- 安装器生产 URL 只接受 HTTPS；non-force 把 dangling symlink 视为 existing。
  最终目录项提交在有 Perl时采用 `link(2)` atomic no-replace，force 采用
  `rename(2)`；Linux 无 Perl时使用 `ln -T`/`mv -T` no-target-directory fallback，
  缺少安全 primitive 时失败关闭。directory、symlink-to-directory 与预检后竞争必须
  拒绝；归档中目标 executable member 必须恰好一个，重复 member 必须拒绝。
- Homebrew formula 与公共 fixture repo 内容只在后续公开 Go/No-Go 后创建远端对象；本轮可以在本地 staging 目录验证。

## 8. 验收门禁

1. 全部新增只读命令证明零写；需要网络的命令证明请求范围与零下载。
2. v1→v2、activation、policy、retention、repair 和 support privacy 单测通过。
3. 现有 WAL/doctor/store 安全测试无回归。
4. macOS 与 Linux ordinary/race 通过，四目标 build 和双构建一致。
5. 安装器、release snapshot、LICENSE/notices/SBOM 检查通过。
6. 文档、代码、change record 与 verification report 一致。
7. pinhaoma-review verdict 为 pass，或所有 partial/fail 在 RC 前关闭。
8. GitHub-hosted CI 若因 private Billing 未执行，必须标为 external gate；不得称为通过。

## 10. 非目标
