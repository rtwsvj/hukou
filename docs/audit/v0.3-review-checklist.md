# V0.3 external review checklist

## Priority model

- P0: loss/replacement of unrelated user executables, arbitrary code
  execution, secret disclosure, or release of unverified artifacts.
- P1: corruption or unrecoverable loss of hukou-managed state; trust-boundary
  bypass; rollback/repair converges to the wrong bytes.
- P2: fail-open behavior, misleading read-only/verification claims,
  reproducibility or portability defects with realistic impact.
- P3: hardening, coverage, documentation, or usability weakness without an
  immediate safety failure.

Record “no finding” only after checking the relevant seam; an unchecked box is
not evidence of safety.

Items labeled as known/open are audit leads, not pre-judged vulnerabilities.
The reviewer must confirm exploitability, preconditions, and severity.

## A. Filesystem ownership and path safety

- [ ] Adopt rejects package-manager-owned, non-regular, non-executable,
  special-mode, duplicate-name/path, and hostile store topologies before state
  mutation.
- [ ] Name, tag, original, temporary, transaction, and destination components
  cannot escape through `..`, slash/backslash variants, case aliases,
  symlinks, hard links, or post-check replacement.
- [ ] Atomic no-replace and force-replace behavior is correct on both Darwin
  and Linux, including the no-Perl Linux fallback.
- [ ] Active-file replacement never follows a symlink to an external file or
  directory and never moves the prepared binary inside a directory target.
- [ ] Same-user race windows are identified precisely; do not assume current
  rechecks are equivalent to directory-fd/`openat` anchoring.
- [ ] The configured store root is an acceptable trust anchor. Current code
  permits the root itself to be a deliberate symlink while rejecting symlinked
  children; review replacement and privilege-boundary scenarios explicitly.

Known open hardening: directory-fd path anchoring is not implemented.

## B. Manifest, policy, and history integrity

- [ ] Schema 0/1 migration is deterministic and cannot smuggle v2-only fields.
- [ ] Schema 2 rejects unknown/missing fields, invalid timestamps/digests,
  duplicate names/paths, broken/forward lineage, unsafe tags, and tag-to-SHA
  rebinding.
- [ ] Duplicate JSON object keys receive explicit adversarial review; current
  code does not claim to reject them.
- [ ] Default and explicit rollback follow logical ancestors after arbitrary
  upgrade/rollback sequences and never use mtime as authority.
- [ ] Policy changes are atomic, lock-aware, pending-transaction-aware, and do
  not touch the live binary.
- [ ] SemVer normalization, channel selection, pin precedence, pagination
  limits, and downgrade refusal cannot produce a silent wrong target.
- [ ] V0.2 downgrade behavior after schema-v2 writes is documented and safely
  rejected rather than silently lossy.
- [ ] Manifest loading has a defensible byte/entry/history limit. Current
  regular-file loading uses an unbounded read and activation history is not
  compacted, so resource-exhaustion behavior needs explicit review.

## C. Transaction, durability, and recovery

- [ ] PREPARED recovery converges every participant to before-state; durable
  COMMIT converges to after-state across every live/manifest combination.
- [ ] Every intent payload, commit marker, rename, link, removal, and directory
  update has the required durability ordering for the supported filesystems.
- [ ] Recovery is idempotent after process kills at each write/rename/sync
  boundary.
- [ ] External drift is rechecked immediately before destructive operations;
  unknown state retains evidence and does not overwrite it.
- [ ] Store write-once, original immutability, retry, cleanup, and prune
  durability cannot alias or delete current/recovery bytes.
- [ ] Claims are limited to process-crash behavior; hardware cache reordering,
  disk corruption, and hostile same-user writers are not silently implied.
- [ ] The threat model proves the data root is owned exclusively by the same
  trusted identity. Journal intent currently validates absolute/clean/unique
  paths but does not independently bind every operation/role/path to the
  current manifest or an allowlisted resource set; audit low-privilege-writable
  data roots and any elevated execution scenario.

## D. Repair and diagnostics

- [ ] Only the two documented repair actions are reachable.
- [ ] Plans bind action, data-root identity, full relevant fingerprint, and
  preconditions without leaking the absolute data root.
- [ ] Any fingerprint-covered relevant state difference present at apply time
  makes apply fail before business-state write.
- [ ] Plan replay/freshness is intentional. Unrelated state is outside the
  fingerprint, `generated_at` is not an expiry, and a state that returns
  exactly to the captured observation may make an older plan applicable again.
- [ ] Backup restore uses the same strict manifest decoder as the primary path
  and verifies live bytes before acceptance.
- [ ] `doctor`, inspection paths, and support collection never trigger implicit
  repair or transaction recovery.
- [ ] Support output excludes raw path/repo/tag/name, usernames, HOME,
  environment, tokens, binaries, WAL payloads, and stable identifiers that
  would defeat anonymization.

Known boundary: stale repair apply may still create/use the lock file.

## E. Network and untrusted release input

- [ ] Drift checks occur before GitHub metadata requests and all read-only
  metadata paths avoid asset downloads.
- [ ] API tokens are sent only to the intended API host and never to download
  hosts or redirected origins.
- [ ] API/download clients enforce total timeout, retry caps, redirect policy,
  content-length/stream limits, and bounded release pagination.
- [ ] Download size is globally bounded even when the API declares a positive
  asset size. Current code uses the declared size as the cap and applies the
  512 MiB default only when size is unknown; test abnormal multi-gigabyte
  declarations and available-disk exhaustion.
- [ ] GitHub API JSON bodies cannot exhaust memory. This is a known open item:
  there is no dedicated response-body byte cap yet.
- [ ] Archive formats reject traversal, ambiguous roots, duplicate targets,
  unsupported containers, executable-format confusion, and decompression
  bombs.
- [ ] The Go extractor's 512 MiB bounds and the shell installer's separate
  limits are reviewed independently.
- [ ] The Go tar first pass has member-count and total decompression-work
  budgets. It currently scans the complete stream to select one target while
  the 512 MiB cap applies to the selected output entry, not all discarded
  content or headers.
- [ ] The shell installer's `curl` calls have acceptable connect/total timeout,
  redirect-host, and maximum-file-size policies; HTTPS protocol restriction
  alone is not treated as all network bounding.

Known open hardening: Go pre-scan and shell-installer-wide decompression/member
budgets are not implemented; API JSON and manifest reads also need byte caps.

## F. Installer and release supply chain

- [ ] Installer production URLs require HTTPS, file fixtures require explicit
  opt-in, checksums cover the exact chosen archive, and missing/malformed
  evidence fails closed.
- [ ] Publisher checksum limitations are stated: same-channel checksums are
  integrity evidence, not an independent signature.
- [ ] The product policy for releases with no publisher checksum is accepted
  explicitly. Current real upgrade warns and continues using a locally
  computed post-download hash; decide whether a flagship public default must
  fail closed or require an opt-in.
- [ ] Release script rejects dirty trees, derives commit/date from Git,
  normalizes archive metadata, includes all license/notices files, and emits
  exactly four expected targets.
- [ ] Two clean builds are byte-identical under a recorded Go/GNU tar
  environment; mismatch investigation does not stop at archive hashes.
- [ ] SBOM generation scans extracted packaged binaries rather than archive
  containers and validates four binaries plus expected modules.
- [ ] Manual workflow dispatch cannot publish a Release; pushed tags must be
  annotated, point to main, and match the packaged commit.
- [ ] Public publication cannot bypass successful packaging and public-only
  attestation; action SHA pins and minimal permissions are independently
  reviewed.
- [ ] The lifecycle check covers private tag/Release followed by a later
  visibility change. A Release created while private can skip attestation and
  would become visible with the repository unless explicitly prevented,
  deleted, or attested before the visibility transition.
- [ ] Release reproduction distinguishes declared Go 1.26.2 compatibility
  from the historical Go 1.26.5 artifact hashes.

Unclosed gate: this RC has no executed GitHub-hosted CI, public CodeQL, public
attestation, published V0.3 assets, or independent signature.

## G. Tests, portability, and documentation

- [ ] Ordinary and race tests pass uncached on macOS and Linux at the exact
  subject SHA.
- [ ] The declared Go 1.26.2 toolchain passes independently. Hosted workflows
  derive the version from `go.mod`, but the recorded local evidence used Go
  1.26.5 and the hosted jobs never started.
- [ ] Linux is run non-root with a read-only source tree; fixture behavior does
  not depend on root privileges or writable source/module caches.
- [ ] Coverage is interpreted by risk, not headline percentage. The recorded
  total fell from 73.8% to 72.9% while the code surface grew.
- [ ] Public-network fixture behavior, rate limiting, and CDN redirects are
  tested separately from `httptest` simulations before public release.
- [ ] Windows and Homebrew are described as unsupported/unimplemented, not as
  implied by cross-compilation or roadmap entries.
- [ ] README, CLI help, specs, ADRs, workflows, and code agree on read/write,
  network, rollback, repair, release, and visibility semantics.

## H. Launch decision

Do not recommend public release until the report explicitly addresses:

1. independent reproduction of the fixed subject;
2. restored and green hosted CI on the intended commit;
3. public CodeQL and artifact-attestation behavior;
4. public-network/fixture smoke or an explicit accepted exception;
5. disposition of P0/P1 findings and every known hardening item above;
6. exact merge/tag/Release/visibility sequence with rollback boundaries.

The internal pre-handoff review did not retain a standalone raw report and
cannot close these external questions. Require the external report to state
which items were exercised, not merely that this checklist was read.
